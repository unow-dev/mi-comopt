# バッチ処理・QAワークフロー

## 0. 入力検証

入力がJSON配列で、各レコードに `username` / `handle` / `comment` / `postedAt` / `postedDate` が存在することを確認する。既存値は変更しない。

## 1. 回帰照合

前回確定データと5フィールド完全一致するレコードを抽出し、そのラベルを固定継承する。変更・新規分だけを判定対象とする。

## 2. 全体handle索引

500件に切る前に、更新版全体を`handle`完全一致で索引化する。差分入力の場合は、前回参照データの同一handle履歴も確認できるようにする。

## 3. バッチ化

推奨サイズは500件。件数が大きくても、判定文脈の境界にはしない。

## 4. 多段階判定

前回実績の順序を維持する。

1. 明白な`nuisance`
2. 嘲笑・羞恥
3. 有害な決めつけ
4. 性的対象化再監査
5. 同一handle反復監査
6. コメント欄内対人攻撃
7. `normal`残存監査
8. 表記揺れ・類似表現一貫性監査

## 5. 境界アンカー照合

新規・曖昧コメントは `golden_boundary_examples.json` の近似例を確認する。語だけでなく、その例がなぜ`normal`/`nuisance`になったかを比較する。

## 6. 最終機械検証

- 入出力件数一致
- 全件`label`存在
- `label`は`normal`/`nuisance`のみ
- 5フィールド完全一致
- 入力順維持
- 追加フィールドは`label`のみ
- 前回と5フィールド完全一致したレコードのラベルが前回確定値と一致

`tools/validate_output.py` を使用する。

## 7. 完了報告で残す情報

- 入力件数 / 出力件数
- `normal` / `nuisance`件数
- バッチサイズ / バッチ数
- 全体handle索引を使ったか
- 各監査Passを実施したか
- 機械検証結果
- 入出力SHA-256
- 前回完全一致レコード数とラベル不一致数（不一致は0が原則）
