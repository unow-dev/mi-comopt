# Stage 13 次回更新ラベル付 Handoff

このZIPは、次回の更新版TikTokコメントデータを、2026-08-24時点のStage 13確定結果と可能な限り同じ評価基準でラベル付するための引き継ぎ一式です。

## 最重要ルール

1. **仕様を最上位の意味基準にする。** `specs/01_選別基準仕様_Stage13.md` と `specs/02_ラベル付作業ルール仕様_Stage13.md` を先に読む。
2. **既存5フィールド完全一致のレコードは、前回確定ラベルをそのまま継承する。** モデルの再解釈で過去ラベルを変更しない。
3. **新規・変更レコードだけを再判定する。** ただし同一`handle`履歴は、更新版データ全体＋必要なら過去参照データを横断して確認する。
4. **同一本文だけでラベルを固定しない。** 同じ本文でもhandle履歴によりラベル差が生じ得る。前回実例は `reference/repeated_handle_case_studies.json` を参照。
5. **500件バッチは作業単位であって判定文脈の境界ではない。** handle履歴索引はバッチ化より先に全体で作る。
6. **最終出力は既存5フィールドを完全保持し、`label`のみ追加する。** `normal` / `nuisance` 以外は禁止。

## 推奨実行順

- `tools/prepare_update.py` で更新版を前回確定データと照合する。
- 完全一致レコードは固定継承し、新規・変更分を500件単位で処理する。
- `policy/02_DECISION_BOUNDARIES.md` と `reference/golden_boundary_examples.json` を境界アンカーとして使う。
- handle単位の反復否定・反復性的対象化を全体監査する。
- `normal` 残存監査と類似表現の一貫性監査を行う。
- `tools/validate_output.py` で件数、順序、既存フィールド、ラベル値、過去完全一致レコードのラベル継承を検証する。

## 参照優先順位

1. 前回と5フィールド完全一致するレコードの**確定ラベル**
2. Stage 13公式仕様
3. `golden_boundary_examples.json` の近似事例
4. 同一handle履歴
5. 本文単体の意味判断

この優先順位は「前回結果の再現」を目的とした運用上のものです。仕様そのものを改訂する場合は、別Stageとして管理してください。
