# TikTokコメント ラベル付作業ルール仕様 — Stage 13対応

## 1. 目的
本仕様は「TikTokコメント 選別基準仕様 — Stage 13」に従い、統合JSON全件へ `normal` / `nuisance` を付与する作業手順・処理ルール・品質管理方法を定める。

## 2. 入力レコード型
各レコードは原則として以下の5フィールドを持つ。

```json
{
  "username": "めろんぱん❄️⛄️",
  "handle": "user1250129739194",
  "comment": "早くみれた！",
  "postedAt": "6-26",
  "postedDate": "2026-06-26"
}
```

既存フィールド:
- `username`
- `handle`
- `comment`
- `postedAt`
- `postedDate`

これらを一切変更してはならない。

## 3. 出力
各レコードへ `label` のみ追加する。

```json
{
  "username": "めろんぱん❄️⛄️",
  "handle": "user1250129739194",
  "comment": "早くみれた！",
  "postedAt": "6-26",
  "postedDate": "2026-06-26",
  "label": "normal"
}
```

`label` は `normal` / `nuisance` の2値のみ。

## 4. 絶対条件
- 入力レコードを削除しない
- 新規レコードを追加しない
- 入力順を変更しない
- 全件に `label` を追加する
- `username` / `handle` / `comment` / `postedAt` / `postedDate` を変更しない
- 誤字、表記揺れ、絵文字、改行、空白、日付表記を勝手に正規化しない
- `reason` 等の判定理由フィールドを追加しない
- `uncertain` 等の第三ラベルを作らない

## 5. 判定単位
原則1コメント＝1判定単位。本文を読んで `normal` / `nuisance` を決定する。

ただしStage 13では、同一ユーザーによる反復否定・反復性的対象化を判定材料として使うため、必要に応じて同一 `handle` の他コメントも参照する。

## 6. 同一ユーザー識別
同一ユーザー判定は `handle` 完全一致を使用する。

- `username` が同じでも `handle` が違えば原則別ユーザー
- 表示名の変更・絵文字差だけでユーザーを統合しない

## 7. `postedAt` / `postedDate` の扱い
### `postedAt`
元データ保持用。値を変更・正規化しない。単独では判定材料にしない。

### `postedDate`
元データ保持用であり、必要に応じて同一ユーザーの反復否定・反復性的対象化の時系列確認に使用できる。

ただし以下だけを理由に `nuisance` としてはならない。
- 同日に複数投稿
- 投稿間隔が短い / 長い
- 長期間コメントしている
- 特定日に集中している

時系列は本文上の反復を確認する補助情報としてのみ使う。

## 8. 基本判定手順
### Step 1: 明白な `nuisance`
以下を先に確認する。
- 直接的な侮辱・人格攻撃
- 嘲笑・羞恥付与
- 年齢・容姿・身体・能力等を使った侮辱
- 性的対象化・フェティッシュ要求
- 有害な決めつけ
- 比較による侮辱
- 排除要求
- 脅迫・暴力・死を向ける表現
- 他コメント投稿者への人格攻撃
- 明白なスパム・誘導

### Step 2: 批判対象の確認
`normal` 寄り: 動画、作品、演出、編集、発言、服装、特定行為・表情・企画への批判。

`nuisance` 寄り: 人物そのもの、人格、知能、社会性、人間性、年齢を含む人物価値、身体的価値、存在、活動資格、性的価値への攻撃。

### Step 3: 嘲笑機能の確認
行為批判の形式でも、笑いものにする・恥をかかせる・親や家族を持ち出して羞恥を与える・物真似で嘲る・「一人でこれやってる」等の冷笑が強ければ `nuisance`。

### Step 4: 性的対象化の確認
通常の好意と性的消費を区別する。AV、性的利用、性的隠語、身体部位への執着、フェティッシュ、性行為要求等は `nuisance`。

### Step 5: 他コメント投稿者への攻撃
投稿者を擁護する目的でも、別ユーザーに新たな人格攻撃をしている場合は `nuisance`。通常の反論・擁護は `normal`。

## 9. 同一ユーザーの反復否定チェック
1. 同一 `handle` の全コメントを集約する。
2. 否定・嘲笑・嫌悪・皮肉・冷笑・人物批判・排除要求等を抽出する。
3. 2件以上確認された場合、作業上「反復否定ユーザー」とみなす。
4. そのユーザーの軽度な否定コメントも再判定する。
5. 反復的嫌がらせの一部として自然なら `nuisance` へ寄せる。
6. 肯定・質問・中立・雑談・応援まで一括で `nuisance` にしない。

必要に応じて `postedDate` 順に並べ、反復の時系列を確認する。ただし時系列だけでラベルを決定しない。

## 10. 反復的な性的対象化チェック
同一 `handle` が複数回、身体・性的含意・フェティッシュ表現を投稿している場合、単体では曖昧な表現も再判定する。

対象例:
- 脇
- 唾液
- 舐める
- はぁはぁ
- 身体物を欲しがる
- 性行為暗示
- 性的隠語

必要に応じて `postedDate` で時系列を確認する。

## 11. 重複コメント
同一本文が複数存在する場合、原則として同じ意味・用法なら同じラベルとする。

ただし、同一ユーザーの反復履歴などが異なるため、同一 `comment` でもラベル差が生じることは許容する。「同じ本文だから必ず同じラベル」という機械ルールにはしない。

## 12. 短文の扱い
例: きつい、無理、痛い、こわい、何してるの、おえ、あざとい。

人物・振る舞い全体への嫌悪・嘲笑として自然なら `nuisance`。具体的な作品・行為評価として自然なら `normal`。同一ユーザーによる反復があれば `nuisance` 側へ強める。

## 13. 引用・報告・擁護
攻撃語が含まれているだけで `nuisance` にしない。

「『キモい』とかコメントするのやめた方がいい」→ 原則 `normal`。

「『キモい』とか言ってる奴の方が頭おかしい」→ 新たな人格攻撃があるため `nuisance`。

## 14. 多言語コメント
日本語以外も同一基準で判定する。外国語だから自動的に `normal` にしない。

## 15. 絵文字・ステッカー
絵文字だけでラベルを決めない。`🤮` のように明確な嫌悪・嘲笑として機能する場合は `nuisance` を検討する。`[ステッカー]` のみで意味不明なら、攻撃性が確認できない限り `normal`。

## 16. スパム判定
以下は `nuisance`。
- フォロー要求
- DM誘導
- 外部サイト誘導
- 不自然な営業
- 無関係な宣伝
- 長文コピペ
- アカウント成長目的の大量誘導

同一ユーザーが普通のコメントを複数回しただけではスパムとしない。

## 17. 判定理由は出力しない
内部では理由を考えてよいが、出力JSONに `reason` 等を追加しない。追加可能なのは `label` のみ。

## 18. 推奨多段階作業フロー
### Pass 1: 明白な `nuisance`
罵倒、脅迫、明白な性的対象化、スパム、排除要求。

### Pass 2: 嘲笑・羞恥
冷笑、親・家族を使う羞恥、一人撮影への嘲笑、年齢嘲笑。

### Pass 3: 有害な決めつけ
承認欲求、媚び、計算、炎上目的等。

### Pass 4: 性的対象化再監査
直接語だけでなく、隠語、身体部位、フェティッシュ、性的利用暗示。

### Pass 5: 同一ユーザー監査
`handle` ごとに反復否定・反復嘲笑・反復性的対象化を確認。必要に応じて `postedDate` 順に確認。

### Pass 6: コメント欄内対人攻撃
ファン攻撃・アンチ攻撃を含む他ユーザーへの侮辱・人格攻撃。

### Pass 7: `normal` 残存監査
最後に `normal` のみ再走査し、取りこぼされた `nuisance` を探す。

## 19. 一貫性チェック
意味的に近いコメント間で不自然なラベル差がないか確認する。

例:
- おえ / おえっ
- 痛い / いたい
- キツい / きつい
- 無理 / むり
- あざとい / あざとすぎ
- おかず / 今日はこれでいい
- AV / エロ系

ただし、本文文脈や同一ユーザー履歴が違う場合はラベル差を許容する。

## 20. 機械チェック
最終出力後、必ず以下を検証する。

### 件数
`入力件数 == 出力件数`

### 全件ラベル存在
全レコードに `label` がある。

### ラベル値
全件 `normal` / `nuisance` のどちらか。

### 既存5フィールド完全一致
各インデックスで以下を確認する。

```text
入力.username   == 出力.username
入力.handle     == 出力.handle
入力.comment    == 出力.comment
入力.postedAt   == 出力.postedAt
入力.postedDate == 出力.postedDate
```

### 順序
同一インデックスの既存5フィールド一致により入力順維持を確認する。

### 不要フィールド
追加可能なのは `label` のみ。意図しないフィールドがないことを確認する。

## 21. 品質上の禁止事項
- 全件を最初に `normal` とし、一部キーワードだけを `nuisance` にする
- NGワードだけで判定する
- 否定語があるだけで `nuisance` にする
- 反復否定ユーザーの全コメントを一括 `nuisance` にする
- `username` / `handle` から人物像を推測する
- `postedAt` / `postedDate` だけで攻撃性を判定する
- 動画内容・返信先等、入力にない文脈を勝手に補完する

## 22. 曖昧な場合
`uncertain` は使用しない。必ず2値から選ぶ。

以下の順で判断する。
1. 本文単体で人物攻撃として自然か
2. 嘲笑・羞恥付与として機能するか
3. 性的消費として機能するか
4. 有害な決めつけか
5. 他者への人格攻撃か
6. 同一ユーザーの反復履歴があるか
7. `postedDate` 上も反復傾向が確認できるか（補助情報）
8. それでも通常の批評・質問・好意として自然か

1〜7が弱く、8が成立するなら `normal`。

## 23. 作業完了条件
- 全レコード判定済み
- Stage 13選別基準適用済み
- 同一ユーザー反復監査済み
- 必要に応じた `postedDate` 時系列確認済み
- 性的対象化再監査済み
- コメント欄内対人攻撃監査済み
- `normal` 残存監査済み
- 表記揺れ・類似表現の一貫性監査済み
- レコード件数一致
- 入力順維持
- 全件 `label` 存在
- label enum正常
- 既存5フィールド完全一致
- 余計なフィールドなし

## 24. 要点
Stage 13では「攻撃語を探す」のではなく、「コメントが誰に対して何をしているか」を判定する。

作業は、コメント単体 → 類似表現 → 同一ユーザー履歴 → 必要に応じた時系列確認 → `normal` 側の再監査、の順で多段階に行う。
