# 候補キーワード更新フローの整備

## 目的

ラベリング済みデータの配置を起点として、候補キーワードの生成・評価・更新を再現可能にするための大枠を整理する。

あわせて、更新によって初めて候補リストに追加されたキーワードを `NEW` として表示できるようにし、候補の新規性を利用者が把握できる状態にする。

## 背景

現在の候補キーワードは、[filterKeywordCandidates.json](../../../../package/src/data/filterKeywordCandidates.json) に直接配置され、[App.jsx](../../../../package/src/App.jsx) がビルド時に読み込んで表示している。

候補データには `direct_nuisance`、`reactive`、`normal` のヒット数や推奨度などが含まれているが、ラベリング済みデータの保存場所、入力形式、評価処理との接続、データの妥当性を検証する仕組みはまだ定義されていない。

そのため、現状は「候補と指標を作成する」「JSONを更新する」「画面から利用する」という手作業中心の流れであり、更新結果の再現性や、どのデータに基づく候補なのかの追跡性を確保しにくい。

なお、ラベリング作業そのもの、ラベル判定基準、ラベリング完了までの運用は本Issueの対象外とする。

## 決定済み大枠

- 議論の起点は、ラベリング完了済みデータを所定の場所へ配置する段階とする。
- ラベリング済みデータの配置ルールとデータ契約を、本Issueの対象範囲に含める。
- データ契約には、保存形式、必須フィールド、型、ラベル値、データセットのメタデータ、スキーマバージョン、検証ルールを含める。
- `labeling_status` などにより、ラベリング完了済みであることを機械的に確認できるようにする。
- データ契約を満たさないデータは、候補キーワード更新処理の入力として扱わない。
- 配置したラベリング済みデータは、後から内容を上書きせず、データセット単位で追跡できる形にする方向とする。
- 候補リストに初めて追加されたキーワードには `introduced_at` を記録する。
- `introduced_at` を基準に `NEW` 表示を判定する。
- `NEW` の表示期間は固定日数ではなく、`new_keyword_display_days` のような設定値で調整可能にする。
- 既存キーワードの推奨度や指標の変更、および既存キーワードへの表記揺れ追加だけでは、新規キーワードとして扱わない。

## 初期考察

ラベリング済みデータは、例えば次のようなスナップショット単位で管理する案がある。

```text
data/
└── labeled/
    └── 2026-08-24/
        ├── comments.jsonl
        └── manifest.json
```

レコードの最小契約としては、次のような構造が考えられる。

```json
{
  "record_id": "comment-000001",
  "text": "コメント本文",
  "label": "direct_nuisance"
}
```

ラベル値は、候補生成・評価で利用する分類値として、少なくとも次を明示的な列挙値として定義する案がある。

```text
direct_nuisance
reactive
normal
```

データセットの `manifest.json` には、データセットID、スキーマバージョン、ラベル定義のバージョン、完了状態、レコード数、完了日時、内容確認用ハッシュなどを持たせる案がある。

候補キーワードJSONは、ラベリング済みデータから生成される成果物として扱い、将来的には候補データを直接手編集しない形が望ましい。ただし、生成処理の責務、評価指標の計算方法、推奨度の判定基準は別途定義が必要である。

配置先をリポジトリ内とするか、サイズ・個人情報・アクセス制御を考慮して外部ストレージに置き、リポジトリでは `manifest` と参照情報のみを管理するかは未決定である。

また、ラベルが単一値か複数値か、`text` 以外に元動画・投稿・取得時点などの情報をどこまで保持するか、評価対象期間と各ヒット数の分母をどう定義するかについても、データ契約の設計時に決める必要がある。
