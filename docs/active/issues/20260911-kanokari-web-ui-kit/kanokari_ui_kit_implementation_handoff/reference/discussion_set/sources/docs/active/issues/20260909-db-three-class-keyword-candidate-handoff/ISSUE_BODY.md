# Issue: Comment DBの3分類ラベルからChatGPT向けフィルターキーワード候補workset-handoffを生成する

## 目的

Comment DBに反映済みの3分類ラベルと、その対象snapshotの観測データを完全一致で結び付け、ChatGPTがフィルターキーワード候補を提案するための検証可能なworkset-handoffを生成できる状態にする。

利用者が対象snapshotを指定する単一のコマンドで、workset-handoffの生成に必要な成果物を一括して作成できる状態にする。

生成したworkset-handoffは、既存のフィルターキーワード候補更新フローへ追跡可能に接続でき、ChatGPTから返却された提案を既存のローカル検証・評価・公開処理へ安全に引き渡せる状態を目指す。

ChatGPTから返却された候補提案を、対象snapshotおよびworkset-handoffとの対応を検証したうえでComment DBへ反映できる状態にする。そのために必要なDB反映スクリプトと、反映に必要なデータの保持方法を設計対象に含める。

Comment DBへ反映された候補データから、UIが参照するJSONデータを生成・更新できる状態にする。そのために必要なUI用JSON反映スクリプトと、DB上の候補データとの対応を確認する方法を設計対象に含める。

本issueで扱うworkset-handoff生成、ChatGPT返却物のDB反映、DBからUI用JSONへの反映の3業務範囲は、相互に疎結合に保つ。それぞれが明確な入出力と検証可能な対応情報を持ち、ある範囲の変更が他の範囲の実装詳細へ直接依存しない状態を目指す。

## 背景

three-class worksetのresponseはComment DBへ反映済みであり、対象の1 snapshotには24,622件の観測データに対する`direct_nuisance`、`reactive`、`normal`の3分類ラベルが保存されている。観測データには、候補選別に必要なコメント本文、ユーザー名、ハンドル、投稿日時および投稿日も保存されているため、フィルターキーワード候補を検討するためのデータはDB上で揃っている。

一方、現在の`export-analysis-input`はraw観測の5項目だけを出力し、保存済みの3分類ラベルを含まない。既存のフィルターキーワード候補ワークフローも、3分類ラベル付きのファイルデータセットを入力としてworkset-handoffを生成する設計であり、Comment DBから直接、候補提案用のデータセット・対象snapshot・内容ハッシュを結び付ける経路はない。

既存のChatGPT提案の返却経路は、`candidate_proposal.json`をローカルの検証・評価・公開処理へ渡すものであり、提案内容とその根拠となるsnapshot・workset-handoffをComment DBへ記録する経路を持たない。返却物をDBへ反映するには、反映対象、検証条件、再適用および訂正時の扱いを定めた反映スクリプトの設計が必要である。

UIは現在、リポジトリ内のフィルターキーワード候補JSONを直接参照しており、Comment DBへ反映された候補データをUI用JSONへ反映する経路はない。DBを候補データの記録先とする場合は、DB反映後のデータだけを入力としてUI用JSONを生成し、表示内容がDB上の確定データと対応していることを確認できるようにする必要がある。

3業務範囲は連続した運用経路を構成するが、生成・反映・表示用データ更新では入力、検証責務および失敗時の扱いが異なる。単一の処理へ密結合させると、返却物の再検証やDB反映の再実行、UI用JSONだけの再生成を独立して行えなくなるため、範囲間の対応情報を保持しつつ各範囲を粗結合に保つ必要がある。

既存の公開済みフィルターキーワード候補は今回のDBラベルとは異なる過去のデータセットに結び付いている。今回の3分類結果を用いる際は、ラベル反映対象のsnapshotだけを選別範囲として固定し、ChatGPTへ渡すworkset-handoffとローカルで検証・評価・公開するデータが同一であることを確認可能にする必要がある。
