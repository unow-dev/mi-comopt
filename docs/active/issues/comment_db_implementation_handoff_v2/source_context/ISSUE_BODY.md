# 現状のデータ更新フロー整理

## 目的

現在のデータ更新について、rawデータの収集・統合から、コメント分類、フィルターキーワード候補とブロックアカウント候補の更新、公開用データの生成、webページへのデプロイまでの流れを整理する。

各工程の入力・出力、データの正本、判断者、検証点および工程間の依存関係を明確にし、更新作業の全体像と現在の運用上の課題を共有できる状態にする。

## 背景

現在の更新フローでは、人間が収集したrawデータを入力として、既存データとの統合や重複の扱いを決定し、Comment DBへコメント原本と観測データを保存する。その後、既存の分類結果を引き継ぎながら追加分類用のworksetを生成し、ChatGPTによる3分類と人間によるレビューを経て、分類結果をDBへ反映する。

分類済みデータはフィルターキーワード候補の提案資料に変換され、ChatGPTの提案をローカルで検証・評価して候補データを更新する。さらに、更新済みのキーワード候補と同じ対象コメント・分類結果をもとにブロックアカウント候補を生成し、両候補を含む公開用データを作成してwebページへ反映・デプロイする経路が存在する。

一方で、raw入力、Comment DB、ファイルシステム上の候補publication、公開用artifactおよびGitHub Pagesの配信データが工程ごとに分かれており、どのデータを正本として次工程へ渡すかが一つの更新フローとして整理されていない。最新分だけを更新対象とするのか、過去分を含む統合snapshotを再生成するのか、既存ラベル・候補・provenanceをどのように引き継ぐのかも、作業時に確認が必要になっている。

また、分類や候補採用などの人間による判断、ローカル処理による検証、DBへの反映、公開用artifactの生成、ビルドおよびデプロイ後の確認が複数の資料・コマンド・公開経路に分散している。工程の境界や確認結果が更新単位で追跡しにくく、入力と公開結果の対応関係、更新漏れ、重複処理および未承認データの公開を確認するための前提が不明確になり得るため、現状のデータ更新フローを一連の流れとして整理する必要がある。
