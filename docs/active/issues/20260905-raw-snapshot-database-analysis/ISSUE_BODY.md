# raw snapshot拡張とデータベース起点の分析処理

## 目的

TikTokから取得したraw snapshotを新しいデータ型として保存し、そのraw snapshotから正規化したデータをデータベースへ蓄積し、データベースから取得したデータを後続のラベリング、分析および候補生成処理へ一貫して渡せる状態にする。

取得元のデータ、正規化済みの保存データおよび分析・加工によって生成されるデータの責務と依存関係を分離し、取得項目の追加や分析処理の変更が相互に不要な影響を与えない構成を確立する。

## 背景

現行のComment DBは、`source`、`postRef`、`collectedAt`、`commentText`からなる正規化済みJSONをSQLiteへ保存する独立したインポート機能として実装されている。一方、候補分析処理はdataset JSONをファイルから直接読み込んでおり、データベースから取得したコメントを分析・加工処理へ渡す経路はまだ存在しない。

今回の入力として、取得日時、取得元、動画情報、統計情報、投稿者情報、音楽情報およびコメント一覧を含むTikTokの取得結果をraw snapshotとして扱う。コメントには本文だけでなく、動画ID、コメントID、親コメントID、ユーザー名、ハンドル、投稿日時、いいね数および返信数などの項目が含まれる。コメント一覧は取得時点で読み込めた範囲であり、報告されている総数と一致しない場合があるため、取得範囲を示す情報もデータの一部として扱う必要がある。

また、現状のrawデータ型に存在しない項目であっても、今回から取得・保存対象とするものは新しいraw schemaの追加データとして導入する。既存データとの互換性だけを理由に項目を破棄したり、分析処理側で推測して補完したりせず、取得した値と欠損状態を区別して保持する必要がある。

raw snapshotを直接分析処理へ渡す構成では、取得元の形式変更が分析ロジックへ波及しやすく、取得時点の再現性や過去データとの比較も難しくなる。そのため、raw snapshotを保存上の原本とし、分析に必要なデータを正規化してデータベースに蓄積し、後続処理はデータベースの読み取り境界を介して利用する構成が必要になる。

## 初期考察

- raw snapshotは取得元から得たJSONを改変せず、取得日時、取得元URL、schema versionおよび内容ハッシュとともに保存する。
- 添付された取得結果に含まれる`extractedAt`、`source`、`video`、`stats`、`author`、`music`、`comments`などを新しいraw schemaの正式な構成要素として扱う。今回追加する項目は既存型との差分ではなく、今後の取得データにおける追加項目として定義する。
- raw snapshotから、動画、投稿者、コメントおよびコメントの取得観測を分析用の正規化データへ変換する。rawデータの保存と正規化データの保存は、再処理できるように対応付ける。
- `extractedAt`は取得時点、`postedDate`や`postedAt`はコメントの投稿時点を示す情報として区別する。取得時刻が不明な値を推測して補完しない。
- `commentId`や`userId`が空の場合は、本文や他の項目から推測したIDを作成しない。安定した識別子がない観測は、取得snapshot内の位置や保存時の観測識別子で追跡する。
- `loadedCount`、`reportedCount`および取得範囲を示す注記を保持し、取得できたコメント一覧を動画の全コメントと誤認しないようにする。
- ラベル、検出キーワード、候補評価および公開状態はrawデータではなく、データベースから取得したデータに対する後続の分析・加工結果として管理する。
- データの流れはCollectorまたは取得処理、raw snapshot保存、正規化・DB保存、DB読み取り、分析・加工、artifact生成およびUI表示の順序とする。
- 分析・加工のコア処理はSQLiteなどの具体的なDB実装へ直接依存せず、DB読み取り用の境界または分析入力モデルを介してデータを受け取る。UIもDBを直接参照せず、分析・加工後のartifactを参照する。
- 現行の正規化入力契約、SQLiteスキーマおよびdataset JSONを直接読む候補処理との対応を整理し、raw schemaのバージョン変更とDBスキーマのマイグレーションを追跡可能にする。
