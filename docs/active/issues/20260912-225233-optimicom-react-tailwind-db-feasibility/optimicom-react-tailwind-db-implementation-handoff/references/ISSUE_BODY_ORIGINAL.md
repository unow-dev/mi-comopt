# Issue: Optimicom React + Tailwind UIを現行DB正本で段階実装する

## 目的

`optimicom-react-tailwind` を、サンプル値に依存せず現行DBを正本として利用する本番向けUIへ移行する。第一段階では現行の3分類データを対象に、DBから導出した集計・推奨・候補を表示し、コピー済み・ブロック済みの状態を暫定的に保持できる状態を実現する。6分類への対応は、必要なラベルと契約が整った後の別段階で行う。

## 背景

対象UIは現在、`src/data.js` などに定義されたサンプルデータ、固定表示値、固定チャート、固定文言および画面内のローカル状態を利用している。現行DBからの取得・集計や、DBに基づくアカウント候補の再生成は行っていない。

現行DBには3分類の観測・ラベル・キーワード公開情報が存在する一方、6分類へ可逆的に変換できるラベルや契約は存在しない。DBの集計では、アカウント候補は現行生成物の54件ではなく60件となり、同じ観測データから生成物を再現できない差異も確認されている。また、現行DBのキーワード公開候補は86件であり、UIのサンプル表示件数とは一致しない。

そのため、初回実装の対象を現行3分類に限定し、DBを正本として生成物との差異を解消できる実装へ移行する必要がある。

## 決定済み方針

- 現行UIの `/home/uya/Workspace/tiktok-filter-keywords/package/src/ui` は完全に無視し、実装対象および実装方針の参照元に含めない。
- 分類対応は段階導入とし、第一段階では現行の3分類データおよび生成物を表示する。6分類は、6分類ラベルと必要な契約が整った後工程で対応する。
- サンプルデータは本番表示に使用しない。必要な実データが利用できない場合は、空値・未算出・データ不足として扱う。
- 実現可能性は、必要な材料がDBに存在し、決定的なSQLまたは変換処理で導出できることを基準とする。
- DBを正本とし、UIはDB上の現行公開情報およびラベル情報を利用する。JSONなどのチェックイン済み生成物はDBから生成される出力として扱う。
- 集計単位は観測単位とする。同一テキストや同一対象の繰り返し観測も、重複排除せず観測行として扱う。
- 欠損期間は0として表示する。
- アカウント候補は現行DBのラベルから再計算し、DBから得られる60件を正本とする。空のハンドルは候補から除外し、候補生成の実行記録と根拠となる例を保存する。
- 投稿文・ハンドル・投稿日を用いて運用し、重複・同日投稿の順序・履歴に関する限界をUI上で開示する。
- スコア、総評および推奨は決定的なルールに基づいて算出し、入力値と算出結果を保存する。
- 推奨は算出結果をそのまま表示し、現在のリスク表示を推奨表示へ変更する。
- コピー済み・ブロック済みの状態は、暫定的にローカルストレージを利用して永続化する。
