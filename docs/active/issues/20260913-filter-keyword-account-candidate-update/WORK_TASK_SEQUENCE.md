# Work Task Sequence: フィルターキーワード候補・ブロックアカウント候補の更新からwebページへのデプロイまで

## Purpose

人間が収集したコメントを根拠として、フィルターキーワード候補とブロックアカウント候補が同じ対象データと確定済みの分類結果に基づいて更新され、検証・承認済みの候補を掲載するwebページがデプロイされている状態にする。

## Task Sequence

- [ ] 1. 更新対象コメントの収集範囲で、人間が、コメント収集作業を行う。
- [ ] 2. 更新前確認の範囲で、AIエージェントが、収集データの形式・対象期間・収集範囲、既存データとの関係、および現在の候補更新・公開経路を確認する。
- [ ] 3. 更新条件の範囲で、人間が、今回の対象データ、既存データを含める範囲、および分類・候補選定・公開条件に関する未決事項を決定する。
- [ ] 4. コメント原本と観測データのDB反映範囲で、AIエージェントが、収集したコメント原本と観測データをComment DBへ保存し、決定した更新範囲に対応する保存件数と対象データの参照情報を確認する。
- [ ] 5. コメント分類準備の範囲で、AIエージェントが、DBに保存されたコメントと既存の分類結果を確認し、追加分類が必要なコメントと分類作業に必要な資料を整理する。
- [ ] 6. コメント分類依頼の範囲で、人間が、分類対象と分類作業用の資料をChatGPTへ渡し、コメント分類を依頼する。
- [ ] 7. コメント分類の範囲で、ChatGPTが、渡された分類規則と過去の分類例に基づいて対象コメントを分類し、指定形式の回答を生成する。
- [ ] 8. コメント分類レビューの範囲で、人間が、ChatGPTから返却された回答を保存し、分類結果と判断が必要なコメントの扱いを確認・決定する。
- [ ] 9. コメントの3分類ラベルのDB反映範囲で、AIエージェントが、分類回答を検証して対象コメントの3分類ラベルをComment DBへ反映し、反映件数と更新対象全体のラベルに欠落・競合がないことを確認する。
- [ ] 10. フィルターキーワード候補の提案準備の範囲で、AIエージェントが、DBに反映済みのコメント・3分類ラベルと既存候補に基づく提案用資料を作成する。
- [ ] 11. フィルターキーワード候補の提案依頼の範囲で、人間が、提案用資料をChatGPTへ渡し、候補の更新提案を依頼する。
- [ ] 12. フィルターキーワード候補の提案範囲で、ChatGPTが、分類済みコメント、既存候補および候補生成規則に基づき、必要な候補の追加・更新・廃止・再有効化を指定形式で提案する。
- [ ] 13. フィルターキーワード候補の意味レビューの範囲で、人間が、ChatGPTから返却された回答を保存し、提案内容と判断が必要な候補の扱いを確認・決定する。
- [ ] 14. フィルターキーワード候補の更新範囲で、AIエージェントが、候補提案を検証し、既存候補と提案候補の評価および候補データの更新を行う。
- [ ] 15. フィルターキーワード候補のDB反映範囲で、AIエージェントが、検証済みの候補一覧・提案・参照情報をComment DBへ保存して現在の候補データを更新し、候補件数および対象データ・更新履歴との対応を確認する。
- [ ] 16. ブロックアカウント候補と公開データの生成範囲で、AIエージェントが、DBに反映済みのフィルターキーワード候補と同じ対象コメント・3分類ラベルから、選定条件に従うブロックアカウント候補と両候補の公開用データを生成する。
- [ ] 17. 候補更新結果の確認範囲で、AIエージェントが、両候補の追加・変更・除外、件数、選定根拠、および公開条件との適合を整理する。
- [ ] 18. 候補の採用判断の範囲で、人間が、更新差分と選定根拠を確認し、両候補の採用内容および修正の要否を決定する。
- [ ] 19. webページへの反映範囲で、AIエージェントが、採用内容を公開用データへ反映し、画面の参照先とデプロイ経路を今回の公開データに整合させる。
- [ ] 20. デプロイ前検証の範囲で、AIエージェントまたはCIが、DB反映結果と公開データの対応、両候補の表示・操作、必要なテスト、ビルド、および配信成果物を検証する。
- [ ] 21. デプロイ判断の範囲で、人間が、公開対象と検証結果を確認し、webページへのデプロイを承認する。
- [ ] 22. 更新結果記録の範囲で、AIエージェントが、入力と分類結果の参照情報、各DB反映の結果・件数、両候補の更新差分、検証結果、承認内容、および公開予定の成果物を記録する。
- [ ] 23. デプロイ準備の範囲で、AIエージェントが、承認済み成果物と公開先を照合し、デプロイ対象を確定する。
- [ ] 24. webページの公開範囲で、AIエージェントまたはCIが、webページへのデプロイを実行する。

## Work Notes

- 本文書は更新作業の実行前に作成した作業タスク列であり、全タスクを未完了としている。実行時は完了したタスクだけを `[x]` に更新し、判断・差戻し・検証結果はこの節に記録する。
- 作業者の「AIエージェント」はリポジトリ内で資料生成・ローカル検証・データ反映を行う担当を指し、「ChatGPT」は人間から渡された資料を使ってコメント分類とキーワード候補提案を行う外部の担当を指す。人間がChatGPTへの依頼、回答の保存・レビュー、採用判断および公開承認を担う。
- タスク1で収集した原本、収集元、対象期間、および全件取得か追加分だけかを確認する。現行の候補生成と新UI公開データ生成は単一snapshotを対象とするため、新規収集分だけで既存の対象範囲を置き換えないよう、タスク3で対象範囲を明確にする。複数snapshotの統合が必要な場合は、対応方法と受入条件を決定してから候補生成へ進む。
- DB反映では、今回使用するComment DBのパスと対象snapshot参照を固定し、取り込み・分類・候補反映・公開データ生成で同じDBと決定済みの対象範囲を使用する。各反映の完了は保存結果を読み戻して確認し、次工程はそのDB反映結果を入力にする。
- タスク4では、収集形式に対応する `import-raw-snapshot`、`import-new-comments`、`import-comment-batch` のいずれかで、原本bytesとsnapshot・コメント観測をComment DBへ保存する。入力SHA、snapshot参照、原本と観測の整合性、保存件数を確認する。同一入力の再取り込みが変更なしとなった場合も、その結果を記録する。契約は [コメントデータベース](../../../../package/docs/comment-database.md) を参照する。
- タスク5の `generate-three-class-workset` は分類資料を生成するとともに、worksetと対象snapshotおよび分類対象から除外したコメントの対応をDBへ登録する。タスク9では回答検証後に `apply-three-class-response` を実行し、登録済みworksetに対応するコメント観測へ3分類ラベルを保存する。追加・変更なしの件数と、更新対象全体のラベル件数・対応関係を確認する。既存ラベルとの競合や分類済みコメントの除外によって未ラベルの観測が残る場合は、対応を解決してからタスク10へ進む。
- タスク6では分類用worksetをChatGPTへ渡す。タスク7では、ChatGPTが `RULES.md` を分類規則、`HISTORY.json` を参考例として、`ITEMS.json` の全IDを一度ずつ `direct_nuisance`・`reactive`・`normal` のいずれかに分類する。`workset_id` を保持し、`response.schema.json` に従う単一のJSONだけを回答する。契約は [コメント分類プロンプト](../../../../package/templates/three-class-workset/PROMPT.md) を参照する。
- タスク11では候補提案用handoffの `prompt.txt` をメッセージとして貼り付け、指定の9ファイルを添付する。ローカル検証用の `handoff_manifest.json` は添付しない。タスク12では、ChatGPTが `request_id` と `input_fingerprint` を保持し、必要な `add / update / retire / reactivate` だけを含む提案JSONを回答する。変更不要なら空の `actions` を返す。候補IDの新規発行や評価指標の計算はローカル処理が担う。契約は [候補提案契約](../../../../package/contracts/candidate-handoff/v1/PROMPT_CONTRACT_v1.md) を参照する。
- タスク8・13ではChatGPTの回答を未編集で保存する。回答の形式不正、対象の欠落、既存判断との競合、またはレビューで修正が必要になった場合は、該当する準備・依頼・回答生成へ戻り、再取得した回答を検証する。追加分類対象がない場合は、タスク6〜8が実施不要であることと確認結果をこの節に記録する。
- キーワード候補は、タスク10の `generate-keyword-candidate-handoff` で提案用資料を生成し、タスク14の `full-update` でローカルの候補publicationを検証・評価・更新する。続くタスク15で `apply-keyword-candidate-publication` を実行し、候補一覧、提案、生成要求、manifestおよび対象snapshotとの対応をComment DBへ保存する。候補状態と履歴の正本は既存のfilesystem publicationであり、DBは検証済みpublicationを保持する。DBの現在のrunが今回のrunと一致し、候補件数・入力SHA・親run・参照情報が一致することを確認する。同一内容の再反映は変更なしとして扱い、未検証の回答JSONを直接DBへ取り込まない。コマンド境界は [Comment DB CLI](../../../../package/scripts/comment-database.mjs) と [候補更新スクリプトの説明](../../../../package/scripts/README.md) を参照する。
- 現在の新UI向け経路では、AIエージェントが実行する `export:optimicom-ui` がDB上の現在のkeyword publicationと、それが指すsnapshotの3分類結果からブロックアカウント候補を計算し、両候補・コメント・集計の公開データを生成する。ブロックアカウント候補の保存先は公開JSONであり、現行実装はDBを読み取って候補を導出する。タスク16ではレビュー用の出力先を使用し、タスク19で採用内容に対応する成果物を画面の配信対象へ反映する。候補の修正が必要な場合は、根拠となる分類・提案・選定条件の工程へ戻って再生成し、出力JSONだけを手編集しない。
- 作成時点では、[Vite設定](../../../../package/vite.config.js) は新UIの `optimicom-ui-release.json` を含む公開ディレクトリを使用している一方、[Pages workflow](../../../../.github/workflows/deploy-pages.yml) は従来の `verify:release` と `data-release.json` の公開確認を使用している。タスク19で公開経路と必要な検証を整合させ、タスク20で実際に配信するreleaseと全参照ファイルを確認する。新UI用には `verify:optimicom-ui-release` と `verify:deployed-optimicom-ui-release` が用意されている。
- タスク18・21では、既に決定・承認済みの条件を引き継ぎ、新たな判断が必要な差分を確認する。承認後に候補や成果物が変わった場合は、影響する検証と承認をやり直す。
- 原本、DB、ChatGPT回答、中間生成物は作業用領域で扱う。Gitへ反映する対象は今回の公開に必要な成果物・設定・作業記録として確定し、着手前から存在する別作業の変更を混在させない。
- 現行のPages workflowは `main` へのpushまたは手動実行でデプロイされる。タスク23までに公開先と成果物を確定し、デプロイを開始する操作は終端のタスク24で行う。タスク24の完了条件は、デプロイ処理の成功と、公開URLから取得したreleaseおよび参照ファイルが承認済み成果物と一致することであり、実行結果もこの節へ記録する。
