# 最新raw-dataからGitHub Pagesデプロイまでの更新運用

## 目的

最新のraw-dataを収集し、必要な統合・ラベリング・候補データ生成・検証を経て、キーワード候補およびアカウント候補の最新状態をGitHub Pagesへ反映できる状態にする。

raw-dataの入力snapshotから生成artifact、UIビルドおよび公開済みサイトまでの対応関係を追跡可能にし、最新データに基づく更新を再現可能な一連の運用として完了できるようにする。

## 背景

現在のプロジェクトでは、raw-dataをもとにラベリング済みdatasetを作成し、決定的な候補キーワード・アカウント候補の生成、artifactの検証、React UIのビルドおよびGitHub Pagesへのデプロイを個別に実行できる。GitHub Pagesは`main`への変更を契機にデプロイされるため、生成artifactを更新してpushすれば公開状態を更新できる。

一方で、最新raw-dataの収集開始から、既存データとの統合、過去ラベルの扱い、候補artifactの更新、検証、コミット、デプロイおよび公開結果の確認までを、現在時点の入力と実行結果に結び付けた更新作業として扱う文書化された運用は整っていない。そのため、最新分だけを処理するのか、過去分を含む統合snapshotを再生成するのか、重複や再ラベリングをどのように扱うのかが実行ごとに曖昧になり得る。

また、候補artifactには入力datasetのSHA、生成時点、候補評価結果およびaccount generator provenanceなどの契約がある。raw-dataの差し替えや生成artifactの更新を個別に行うと、入力と成果物の対応関係、既存候補のidentity、過去のprovenanceおよびUIに表示されるデータの整合性を損なう可能性がある。最新データを安全に公開するには、収集したraw-dataから生成物の検証、変更の記録、GitHub Pagesのビルド・デプロイ成功確認までを一つの更新経路として確立する必要がある。
